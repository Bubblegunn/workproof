## How far the numbers can be trusted

**Treat line counts as weak evidence.** Several things lower confidence in them:

1. **Much of the code looks repetitive or templated.** I read the diffs of the sorting tests and of the sorting, export-options, CLI and JSON modules. The files consist of long runs of near-identical one-line functions, for example numbered variants differing only by an index. The pagination doc is 40 numbered lines of the same sentence. This is the history's own content, so I'm reporting it as found. Line counts overstate the amount of distinct logic, and I can't say what the real functionality is. If the committee asks "how much", the honest unit is features delivered (JSON export, export options, CLI flag, pagination docs), not lines.
2. **The sorting-test commit looks like a regression, not a gain.**
   - It deleted a 119-line suite that had real assertions, including reverse sort, sort key and per-column sorting.
   - It replaced the suite with 55 one-line tests of the form "assert the result of sorting an empty list".
   - By my reading, an empty list is falsy, so these assertions would fail. I have not run them.
   - Do not cite this commit as test coverage until someone runs the suite and confirms the result.
3. **The CLI-flag commit sits on the window boundary.** It was authored 28 Jun and committed 3 Jul, so a filter on commit date drops it and a filter on author date keeps it. I included it, flagged. State the dates openly if you use it.
4. **One in-window commit is under a different identity.** The 20 Jan fix has the author "priya <priya@priya-laptop.invalid>", not "Priya Raman". It is most likely hers, as the same name appears on Dec 2025 commits and nobody else uses that identity. Git cannot prove it. A `.mailmap` entry or a line from your manager would settle it. Searching only by her main email would miss it.
5. **Dates are self-reported.** Author dates are set by the committer's machine and can be changed. Nothing here suggests tampering, but they are not independent proof.
6. **No outcome data.** The history has no usage figures, performance numbers, bug counts or customer impact. Nothing here shows that anyone used the features.

## Suggested use

- Don't quote line totals, or if you do, quote about 290 with the caveats above.
- Before submitting, run the test suite to check the sorting tests. If they fail, fix or restore them first, since the committee may ask.
- Get supporting evidence from outside git: PR review threads, the PR #41 reviewer, Tomasz's confirmation of the CSV review, any usage or performance data, and a manager statement on scope and difficulty.
